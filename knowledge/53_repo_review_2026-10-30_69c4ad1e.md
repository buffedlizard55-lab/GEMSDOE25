## 3. Why 0.2778 was highest (B2 lineage, COMPUTED)

Dot-set lineage, from the audit output (`B2 lineage` and `lineage steps`):

* D2.8 (GEMSDOE25/30 file): 44,090 dots.
* H27-4 (GEMSDOE28/31 file): 40,199 dots. Obtained from D2.8 by removing 3,891 dots, all within 1 px of the labelled catalogue.
* B2 (GEMSDOE32 file): 37,654 dots. Obtained from H27-4 by removing 2,545 dots, all within 2 px of the labelled catalogue. B2 is a subset of H27-4 (Jaccard 0.937).
* B2 has **0** dots within 2 px of the labelled catalogue. D2.8 had 6,436 within 2 px.

**Mechanism: INFERENCE, not demonstrated.** A dot that sits next to a mapped fault but not on hidden truth adds false-positive weight under the metric. Removing such dots can raise a pooled DTI score. This explanation is unproven, because:

1. The thinning control (random removal to the same count, with no catalogue buffer) has **not** been run. A random-thinning win would explain the same jump without any buffer effect.
2. The repo's holdout proxy does not reproduce the effect (draws 140–141: B2-style 0.050554 vs H35 control 0.157011; `evidence/h81_exp1/summary.json`).
3. The holdout's "labels" are identical to the catalogue (§5, IR-29-LABELS-EQUALS-CATALOGUE). So the holdout cannot measure recovery of hidden faults.

## 4. Why no new TIF was generated

1. **No candidate passed the gate.** The repo's rule (AGENTS.md rule 5) requires a holdout win over the recomputed comparator in the same run, plus an exact-file audit. No experiment this session produced a candidate, and ~80 prior sessions did not produce a gate-cleared file either.
2. **The holdout is uncertified.** Labels equal the catalogue (§5). A holdout win on these inputs would not establish a competition win.
3. **Lane rule.** B2 has 99.92% of its dots within 3 px of registry raster r13. The literal lane limit is 70%, and the minimum possible at 37,654 dots is 82.70%. Whether this rule binds the competition is an owner decision (IR-29-B2-LANE-VIOLATION-TOP-FILE).
4. **Format is necessary but not sufficient.** A zeros-outside file that passes the local check is still `okay_to_submit: false`, because novelty and performance are unverified and the portal's outside-footprint behaviour is unconfirmed.

Generating a new file under these conditions would produce a file with no validated score. That would contradict the "no hallucination, no unvalidated submission" rule, so it was not done.
